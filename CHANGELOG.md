# Changelog

## Unreleased

### Operator HUD

- The gate reads the firewall ruleset itself every 10 s and publishes it to `$STATE_DIR/firewall_state.json` (atomic, no-follow, 0640, group `kaiacord`); the dashboards read that file and fall back to an audited gate query only when it is missing or stale. An open dashboard no longer adds ledger rows at all, and every request that is still made remains audited (#105). A new `firewall` control reports the lockdown state and the number of Kaia block rules.
- The HUD console's `show audit [--since <N>h]`, `add rule <name> <ioc> [mitre]` and `list recent blocks` work; `help` listed them, but they fell through to "Unknown command". `show audit` lists recent security events with their alert level and reason (read-only); `list recent blocks` shows the active Kaia blocks, folded from the ledger by the same code as boot replay; `add rule` proposes a YARA rule to the gate with a token scoped to `rules/<name>.yar`, and the gate validates it. A test keeps `help` and the dispatcher in agreement.
- Alert levels (`security/alert_levels.py`): every security event type has an explicit level (info, low, medium, high, critical) and a one-line reason; unknown types are medium, never silent. The event feed is coloured by level instead of disposition (a routine sudo exec was as yellow as an unexpected root gain) and shows readable details instead of an 8-character fragment. The HUD's former FIM / PRIV stat (a count of at most three rows) is now critical / high events in the last 24 hours; the curses pane shows the same. Levels are derived when read, so the tamper-hashed event table is unchanged, and they never drive a response. A test fails when code emits an unclassified event type.
- The dashboard's two ruleset readers (rule counts, lockdown state) share one gate query per 10 s instead of polling every 5 and 10 s. Each query is an audited request, so an open dashboard now writes about 8.6k ledger rows a day instead of ~26k (#105).
- The HUD's capability-token cards show tokens again. Since the audit ledger stopped storing raw tokens, rows carry only `capability_token_metadata` with a `fingerprint`; the cards looked for the raw token and its `signature`, so no token issued since then could appear. Cards now carry the SHA-256 fingerprint; no HMAC signature (even of old, expired tokens) is sent to the browser.
- The HUD and curses dashboard no longer re-read the whole audit ledger. The HUD parsed all of it (18 MB, 50k rows on the host) on every 5 Hz snapshot to show the newest 50; it now reads a bounded 1 MiB tail. The dashboard's lifetime token counts follow the file incrementally (restarting on rotation or truncation) instead of re-parsing it every 5 s; on the host ledger they match the old full parse exactly. Both refuse a symlinked ledger.
- The HUD and curses dashboard now show a lockdown while one is in force. They asked `systemctl is-active kaia-lockdown.service`, but that oneshot unit (no `RemainAfterExit`) is "inactive" as soon as the script has loaded the drop-all table, so the `LockdownMode`/`CRITICAL` posture could never appear; every lockdown on 2026-10-30 displayed as "off". The state is now read from the `table inet kaia_lockdown` line of the ruleset the dashboard already fetches through the gate, and shows "unknown" when the gate cannot be asked.

### Network discovery

- InternetDB results are allowlisted before they are cached, shown or appended to asset names (INV-004): hostnames, tags, CVE ids and CPEs must match strict patterns, ports must be 1–65535, and each list is de-duplicated and capped at 64; values that don't fit are dropped. Rows cached earlier are cleaned when read. The enrichment had appended raw tags to otherwise-sanitised asset hostnames.
- Parse NBNS NB and NBSTAT answer records, including scoped/compressed owner names and bounded active/unique node-name extraction; reject truncated or malformed records without partial persistence.
- Reject fragmented IPv4 datagrams and reserved-flag frames before passive UDP discovery parsing; retain support for valid DF-only packets and cover both paths with regressions.
- Fix NBSTAT `NAME_FLAGS` masks: they were bit-reversed (ACT `0x0020`, reserved `0xFF80`), so every real node-status name (Windows sends `0x0400`) was discarded. Now RFC 1002 order: G `0x8000`, DRG `0x1000`, CNF `0x0800`, ACT `0x0400`, PRM `0x0200`, reserved `0x01FF`. Tests use wire values.

### Security

- eBPF after a kernel upgrade (#104): when the running kernel's `/lib/modules/<release>/build` tree is gone (Arch removes it on upgrade), control health reports `ebpf: degraded` (probes still running, but a gate restart before a reboot loads none), and a failed load says `reboot to load the probes` and is logged CRITICAL. The 30 s health cycle re-checks this even without ring-buffer drops. A libbpf CO-RE rewrite was considered and not taken: it removes the header dependency but needs a separate build pipeline and loader for a failure that is now visible and fixed by the reboot the upgrade needs anyway.
- `scripts/kaia-deploy-verify.sh`: one root command deploys the checkout in the required order (install, baseline, start; the gate is disabled if the baseline fails) and runs the host acceptance checks, logging to `/var/log/kaia/`. Root writes only to root-owned paths, never into a user-writable directory.
- The SSH decoy moves from `~/.ssh/authorized_keys.bak` (impossible to create under `ProtectHome=tmpfs`, so the honeypot ran at 4 of 5) to `/var/backups/authorized_keys.bak`, and the gate unit no longer grants write access to `/root/.ssh`. Decoy contents live in `security/decoys.py`; `scripts/install_decoys.py`, run by the installer before the gate starts, creates missing decoys with exclusive no-follow creation at mode 0600 and never touches an existing file (#102).
- Health check, from the first host deployment: `kaia-restore-blocks` inactive with a successful result (the installer stops it; it runs again at boot) is no longer reported as degraded, but a disabled one is, since it would not run at boot. The timer uses `OnActiveSec=5min` instead of `OnBootSec`, which fired immediately when the installer enabled it long after boot, before the gate had been started.
- The executor refuses to block loopback, unspecified, multicast, broadcast and link-local addresses (including IPv4-mapped forms), the host's own addresses, its gateways (read from `/proc/net/route` and `ipv6_route`) and its DNS resolvers. A block is `saddr X drop` on input, so any of these, whether from an injected LLM proposal, honeypot attribution or a replayed ledger record, cut the host off; only address syntax was checked. If those addresses cannot be determined, the block is refused. Unblocking is never restricted. A replayed historical block of such a target now fails visibly in `kaia-restore-blocks`.
- The Policy Gate refuses host changes (`block_ip`, `unblock_ip`, `restart_service`, `write_file`, `run_script`, `add_rule`) when the audit ledger cannot be appended to, and records `audit_ledger_unavailable`. It executed first and audited after, and a failed write was only logged: a block applied then was live but absent from the ledger `kaia-restore-blocks` replays, so it vanished at the next reboot while the caller was told it succeeded. A change whose audit write fails after execution is now returned as an error. Emergency lockdown and read-only diagnostics stay available. The ledger write no longer follows a symlink at the ledger path, the failure log names the action but never the request (which can carry a token), and a new `audit_ledger` control reports the ledger's state.
- Security events can no longer be dropped silently. Event ids were 32 random bits under a PRIMARY KEY, so collisions (likely within tens of thousands of events) discarded detections; ids are now 128-bit, and a collision retries. The database connect had been outside the error handling, so an unopenable database raised into callers that swallow exceptions; `log_security_event` now never raises, logs the full event (type, source, actor, detail) to the journal when it cannot record it, and reports a new `security_db` control as failed until a write succeeds again. Historical rows and their ids are unchanged, so the tamper detector's prefix hash still holds.
- The pacman monitor reports `degraded` in control health, with the reason, when `pacman.log` is missing or unreadable, and `active` again when it can be read; it had stayed `active` while blind.
- Secret-exposure self-check (`security/secret_exposure.py`): every 6 hours (first after 15 minutes) the gate scans its state directory, logs and deployed tree for the live signing secret, byte for byte, and for private key blocks, AWS, GitHub, Slack, Anthropic and OpenAI tokens and a 64-hex `KAIA_CAPABILITY_TOKEN_SECRET=` assignment. Each exposure is recorded once as `secret_exposure` (critical) with file, line and pattern; the matched value is never logged or stored. Documentation example values (the honeypot's `…EXAMPLE` AWS key) are skipped. No symlinks, `.git` or files over 32 MiB. On the host: 332 files, 117 MB, 1.3 s, no exposures. A test keeps the shipped tree clean.
- Installed-content attestation (`security/package_attestation.py`): every 6 hours (first pass 10 minutes after start, postponed during a pacman transaction) the gate verifies every set-user/group-ID file a package installs, PAM modules, the loader, libc, libpam, NSS, the executor's binaries and the Python interpreter against pacman's `mtree` records (type, mode, owner, size, SHA-256), and scans `/usr` for set-user/group-ID files no package owns. Each distinct finding is recorded once as `package_file_altered`, `privileged_file_unowned` (CRITICAL) or `package_file_unverifiable`; alert-only. Mode/owner set by a package's own tmpfiles rule (libutempter) is honoured; `/etc/tmpfiles.d` is not. `scripts/kaia_package_attest.py` runs the same pass on demand. On the host (unprivileged) 155 files verified in 2 s, no alterations, no unowned privileged files. The local package database is unsigned: root can rewrite a record with the file.
- eBPF kprobes are attached one by one instead of by BCC's `kprobe__` auto-attach, so one symbol that is missing or inlined on a kernel no longer disables every probe (honeypots included). A partial load is reported as `ebpf: degraded` naming what is off; the honeypot reports `degraded` when the inode probe is missing; `commit_creds` is only attached together with its exec marker. The openat2 ring buffer grows to 1 MiB (256 KiB overflowed about ten times a day on the host).
- Control health: every control (gate IPC, tamper detection, privilege watch, FIM, YARA, eBPF, honeypots, decoy listeners, discovery, pacman monitor) reports `active`, `degraded`, `off` or `failed` with a detail, and long-running ones send heartbeats. The gate publishes this every 10 s to `$STATE_DIR/control_health.json`; a control that stops beating is `stale`, and one that never reports stays `failed`. The HUD shows a dot per control, the curses pane a summary line, and a failed or stale control moves the posture to `AnomalyDetected`. `kaia-health-check.timer` (new, enabled by the installer) runs `scripts/kaia_health_check.py` every 5 minutes as an unprivileged dynamic user outside the gate; it also flags a gate that stopped publishing and a failed `kaia-restore-blocks`, and fails its unit on anything failed. It never acts.
- The tamper loop survives an exception from an integrity pass. One escaping `check_integrity()` used to end the thread silently, leaving the gate serving with no integrity monitoring.
- Privilege telemetry reports gains of root from `commit_creds()` instead of `setuid()`/`setreuid()` syscall entry. The old probes recorded the requested uid, so the host logged 268 `privilege_escalation` events in 8 days, all sudo (already euid 0) and pacman dropping to the `alpm` user, while missing `setresuid()` and every in-kernel credential change. Now: `privilege_setuid_exec` for a set-user-ID exec (recognised by the exact cred `security_bprm_committing_creds` saw the exec prepare), `privilege_setuid_exec_unusual` when that binary is outside `/usr/{bin,lib,sbin,libexec}`, and `privilege_escalation_unexpected`, logged CRITICAL, for a gain outside execve by a task that held root in none of uid/euid/suid. All are alert-only. The dashboards' privilege alerts show only the last two kinds, from the last 24 hours. Routine `privilege_setuid_exec` records are capped at 60 a minute (a `sudo -n true` loop is one setuid exec and one database write per run, before sudo checks anything); suppressed counts are logged, and the two alert kinds are never capped.
- `tests/test_ebpf_program_compiles.py` compiles the real eBPF program against the local kernel headers (skipped without BCC, so not in CI); with the old missing `<net/sock.h>` it fails with the same error the host logged.
- Alert-only privilege watch (`security/privilege_watch.py`): changes to `/etc/sudoers`, `/etc/sudoers.d/*`, `/etc/passwd`, `/etc/group` and `/etc/ld.so.preload` are logged once with the added/removed lines and recorded as `privilege_config_changed`, or `privilege_config_critical` for a new NOPASSWD rule, a second uid-0 account, new members of a privileged group, or a preload library. It never locks down or blocks startup. State persists in `$STATE_DIR/privilege_watch.json`, so edits made while the gate was stopped are reported at the next start. The HUD feed shows the file path.
- eBPF events use ring buffers with per-stream kernel drop counters instead of per-CPU perf buffers, which dropped events in every exec/unlinkat burst; drops are logged by stream name, and as errors for `honeypot_events`.
- CI runs every `tests/test_*.py` except the documented legacy scripts; `tests/test_ci_covers_all_tests.py` fails when a new test file is not listed. `tests/test_ebpf_ringbuf_drops.py` had been missing from the list since it was added.
- eBPF telemetry compiles again: add `<net/sock.h>`; `struct sock` was incomplete on current kernels, so the whole program (honeypot file watching included) failed to load on every boot.
- Gate unit grants `CAP_BPF` + `CAP_PERFMON` so the probes can load; `CAP_SYS_ADMIN` remains a separate FIM decision.
- Honeypot decoys are also matched by inode at `security_file_open`, catching relative paths, `./file` and recursive greps that never equalled the absolute decoy path; duplicate hits from both probes are reported once.
- Canary flag files `~/flag.txt` and `/root/root.txt` with per-host `KAIA-CANARY-` IDs, installed safely by `scripts/install_canaries.py` and watched as `honeypot_canary_read`. The unit exposes only these two files from home directories (`ProtectHome=tmpfs` + read-only binds).

- `kaia-baseline.sh` aborted after printing its diff whenever any protected file had changed (`diff` exits 1 under `set -euo pipefail`, added in e790749), so a changed tree could never be re-baselined. After a redeploy the Policy Gate then failed its startup integrity check and locked the host down on every restart attempt. The display pipeline is guarded; a behavioural test runs the script's own block under its shell options.
- Enforce timezone-aware, signed capability-token issue and expiry timestamps; reject future-issued, expired, non-positive and over-one-hour tokens, reject malformed signatures, non-string scope/timestamp fields, and excessively nested JSON.
- Preserve the existing capability-token JSON fields and HMAC format. Enforce durable single-use token consumption with an atomic SQLite fingerprint registry; fail closed when the registry cannot be updated. Raw tokens and signatures are not persisted.
- Extend synthetic Policy Gate IPC coverage to fragmented headers/payloads and truncated-frame EOF, asserting incomplete requests close without reaching policy evaluation.
- Restrict HostExecutor subprocess launches to exact registered system-binary paths; reject malformed or NUL-containing argv before spawning a child.
- Load the trusted integrity baseline through a no-follow descriptor; reject symlinks, non-regular files, hardlinks and insecure system-mode ownership/permissions.
- `kaia-restore-blocks.service` loads `/etc/kaia/secret.env`. `core/config.py` exits at import without the signing secret, so the unit failed on every boot and recorded blocks were never re-applied.
- The lockdown table is `inet kaia_lockdown`, not `inet filter` — the stock `/etc/nftables.conf` table has that name, so recovery tooling could not tell the lockdown from the host firewall.
- `kaia-unlock.sh` restores `/etc/nftables.conf` (via `nftables.service`) before `ufw reload` when that service is enabled, and re-applies ledger blocks afterwards; previously a ufw-path unlock left the nftables.conf ruleset and every recorded block missing.
- The capability-token nesting test accepts either rejection path (Python 3.12 raises `RecursionError`; 3.14 parses the list and refuses it as a non-object).
